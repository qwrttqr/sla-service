# Общее описание сервиса

Сервис использует Yandex Geocoder API для перевода текстовых адресов в значения lat, lon и OSRM backend для роутинга
(без учёта пробок), пробки учитываются коэффициентом, подобранным эмпирически)

# Описание архитектуры

## Проект разделён на несколько слоёв

1. API - взаимодействие с сервисом
2. Services - логика
3. Clients - клиенты взаимодействия с внешними API

## По структуре

- `/src/api` - Описание API
- `/src/common` - Ошибки и схемы, используемые повсеместно в проекте
- `/src/core/clients` - Описания клиентов для OSRM бекендов и Yandex Geocoder API
- `/src/core/entites` - Сущности, которыми оперирует логика
- `/src/core/services` - Сервисы, содержащие логику для парсинга CSV, алгоритма диспатчинга заявок, генерации данных,
  взаимодействия с Yandex Geocoder API, взаимодействие с бекендом роутинга
- `/src/infra/clients` - Реализации клиентов для OSRM бекендов и Yandex Geocoder API
- `/src/utils` - Утилиты (например для работы с файловым кэшем)

# Описание алгоритма

Алгоритм получает на вход множество заявок `X` и множество инженеров `Y`, между которыми нужно распределить заявки.

Пошагово:

1. Собираем необходимые множества
2. Сортируем заявки по времени начала, а после приоритета
3. Для конкретной заявки выбираем ближайший офис к данной, после перебираем инжеренеров от данного офиса и проверяем для
   каждого инженера:
    - Набор ограничений
    - Временное окно
    - Факт того, что конкретный инженер обслуживает район, данный в заявке
4. Пытаемся запихать данную заявку во временые окна между уже назначенными заявками с временных ограничений
5. Если мы нашли инженера - добавляем заявку в его расписание и указываем, когда инженер станет свободен (возможно
   такое, что инженер будет некоторое время простаивать, если время открытия заявки позже, чем время освобождения
   инженера). Если же инженера найти не удалось - убираем заявку в неназначенные.
6. Повторяем до момента, пока не пройдём по всем заявкам
